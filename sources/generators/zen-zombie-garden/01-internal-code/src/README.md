# Zombie Garden

Wave-based 3D zombie shooter (perchance). All code lives in `index.html` (single `<script type="module">`); `main.pjs` is the perchance config layer.

## Map Builder (custom maps)
- Lobby button `🗺️ Map Builder` → `builderPanel`; also reachable via a `➕ New Map` card at the end of the Map panel's `mapSelectGrid`.
- **Editor**: a 560px top-down 2D grid canvas (`renderBuilderCanvas`) over a square arena. Name input, S/M/L size buttons (`BUILDER_SIZES = {S:24, M:34, L:44}` — arena half-extent), theme select (`BUILDER_THEMES`: zen / crimson / desert / pale — overrides fog/sky/ground/wall palette of the `MAPS.custom` entry at build time), and a 2-column tool palette (`BUILDER_ITEMS`: crate, barrel, barrier, tree, rock, torch, bush, gravestone, zombie-spawn, player-start, wall-gun, pack-a-punch, mystery-box, aat-machine, erase). Click to place, right-click or Erase tool to remove, `↻ Rotate` (quarter-turns) for rotatable items. `spawn` max 10, `start` max 1, `pap` max 1, `mysterybox` max 1.\n- **Wall guns & machines are player-placeable**: `weapon` and `aat` tools open a sub-picker (`#builderSubSelect`; options in `BUILDER_SUBS` — 11 wall weapons, 5 AAT elements) so each placed station/machine has a `sub` field. **Custom maps contain ONLY the machines the player placed** — there is no auto-fill: a wall gun / PaP / Mystery Box / AAT that isn't placed simply does not exist on the map (rot → `rotY` quarter-turns). `buildCustomItem` early-returns for these types — the shared buildMap loops build the meshes at the player's positions (so wallStations/papPos/mysteryBox/aatMachines arrays + all buy/prompt logic work unchanged). Because `cfg.papPos`/`cfg.mysteryBoxPos` can now be `null` on custom maps, buildMap gates the PaP and Mystery Box blocks on `cfg.papPos`/`cfg.mysteryBoxPos` presence rather than `stationDefs.length` (kept equivalent for built-in maps, which always set them; `cfg.allowMachines = true` lets custom maps build PaP/MB even with zero wall guns).
- **State** lives in `builderState` (module-scoped) + canvas render; saved maps persist in localStorage key `zzg_custom_maps` (`saveCustomMaps`/`loadCustomMaps`): `[{id, name, size, theme, items:[{type,x,z,rot}], created}]`. `renderBuilderMaps` lists them with Play / Edit / Delete.
- **Playing**: `startCustomMap(map)` sets `currentMapId='custom'`, `G.customMapData=map`, then `startGame()`. `buildMap('custom')` merges the theme palette into `MAPS.custom` and calls `buildCustomDecor(cfg)`, which: builds walls at the chosen size (`buildWallsAt`), renders each item in 3D (`buildCustomItem`), and computes `cfg.stationDefs`/`papPos`/`mysteryBoxPos`/`aatDefs` — only from player-placed machines (none auto-scaled; `papPos`/`mysteryBoxPos` are `null` when unplaced, `cfg.allowMachines = true`) before the shared buildMap loops.
- **Gameplay hooks for custom maps**: `G.mapHalf` (player/zombie clamp, default 43), `G.customColliders` (solid items push player & zombies out — added in `updatePlayer` and `updateZombies`), `G.customSpawnPoints` (used by `updateWave` spawns instead of the r=35 ring), `G.customPlayerStart` (player spawn override in `startGame`). All reset in `clearMap`.
- **Zombie-type spawn portals**: the `spawn` tool has a sub-picker (`BUILDER_SUBS.spawn`: normal / fast / tank / frost / fire / sprinter; colors in `ZOMBIE_SUB_COLORS`). Each portal stores its type in `customSpawnPoints` as `{x, z, type}`; `updateWave` passes it to `createZombie(x, z, forcedVariant)`, which forces that variant instead of the wave-probability roll. The 3D portal disc + the 2D canvas marker are tinted per type.
- `renderMap()` appends custom-map cards + the New Map card after the built-in maps (skips the `custom` MAPS entry via `if (id === 'custom') continue`).

## Architecture
- `const MAPS = {...}` (~line 4080) — every map's config (palette, fog, lighting, wall height, weapon-station positions, pap/mysteryBox/AAT spots, music URL). Map grid renders in insertion order.
- `buildMap(mapId)` — switch dispatching to per-map decor builders; sets sky/stars/moon/ground/lighting. Walls built via `buildWalls(cfg)` (default 3 tall; maps can set `wallHeight`).
- Map decor builders: `buildZenGardenDecor`, `buildSanctumDecor`, `buildUndertaleDecor` (before `// === THE ABANDONED OUTPOST ===`), `buildOutpostDecor`.
- `clearMap()` disposes the previous map's objects (including the drifting flower `petals` Points — was leaking across rebuilds).
- Debug hooks: `window._scene`, `window._camera`, `window._renderer`, `window._G` (player: `pos/yaw/pitch`; zombies: `z.mesh.position`), `window._toggleCameraMode`, `window._perfDebug` (`scale`/`auto`/`pixelRatio` — set `auto = false` to stop the adaptive-resolution downscaler), `window._petState`. The renderer is created with `preserveDrawingBuffer: window.__PRESERVE_BUFFER__ === true` (default off); reload with `page_refresh({preambleJs: "window.__PRESERVE_BUFFER__ = true"})` when a screenshot of the WebGL canvas is needed (otherwise captures come back blank).

## Multiplayer (server list / rooms)
- Replaced the old single-global-room MP with a room/server browser. All logic lives in `index.html`.
- **Persistent server list (v-latest)**: rooms are durable, not in-memory. The server script now owns a fixed-layout byte record store in the plugin's durable `state` and `self._rooms` is rehydrated from it on boot (`loadRooms()`), so listed servers survive every player leaving AND server restarts (30-day idle TTL `ROOM_TTL_SEC`, `MAX_ROOMS=256`, `MAX_ROOMS_PER_OWNER=5`, `MAX_ROOMS_PER_NET=12`). Layout: byte 0 = schema version, then `MAX_ROOMS` fixed 72-byte records (`HDR=8, SLOT=72`) — record = id(6) + mode(1) + flags(1) + lastActive(u32) + createdAt(u32) + name(32 ascii) + owner token(16 bytes) + net group(u32) + reserved(4). Helpers: `nowSec/slotBase/readU32/writeU32/hexVal/cleanName/cleanToken/readSlots/writeSlot/clearSlot/loadRooms/freeSlot/evictOne/destroyRoom/countOwned/countNet`.
- **Ownership**: each browser gets a stable 32-hex `mpClientId` (localStorage `zzg_netid`), sent as `hello`/on every room message; the server stores it per-connection (`setOwner`/`ownerOf`) and keeps the first 16 bytes as the room's `owner` token in its slot. `self.rpc.myRooms(clientId)` returns that client's room ids (JSON string) so the client can mark rows **YOURS** and show the 🗑 remove button. `mpMyRooms` mirrors it in localStorage `zzg_myrooms` for instant rendering, re-synced via rpc on connect.
- **Rooms are never deleted on leave** — `leaveRoom` only removes the player, re-hosts (`r.host = first remaining player`), clears `started` when the room empties, touches `lastActive`+`writeSlot`, and re-publishes. Removal happens only via `close_room` (owner token match, or the current host; `destroyRoom(r, true)` publishes `room_gone` to the room and clears the slot) or the empty-room TTL/eviction path.
- Server script (`<script type="text/x-server-plugin">`, starts ~line 1408): rooms in `self._rooms` (id/name/mode/cap/host/started/chat/players/slot/owner/net/createdAt/lastActive), `self._inRoom` per conn, `self._names`, `self._owners`, `self._lastCreate` (1s, replies `room_err` when tripped) + `self._lastChat` (400ms) rate limits, `ROOM_CAP={squad:5,duo:2}`. All clients subscribe to topic `"servers"`; room members subscribe to `"room:<id>"`.
- Server messages: `hello` (clientId); `refresh` → `index`; `create_room` (name/mode/playerName/clientId) → `room` (+`created:true`; refusals = `room_err`); `join_room` (roomId/name/clientId) → `room` (or `room_full`/`room_gone`); `close_room` (roomId/clientId, owner or host only); `leave_room` → `room_left`; `state` (room-scoped relay of x/z/yaw/pitch/hp/wave/kills + a throttled 30s `lastActive` touch); `chat` (room-scoped, 30-msg history); `room_start` (host-only, squad); `room_ready` (duo: all ready → `duo_start`); `duo_down`/`duo_revive`/`duo_over` (duo only). Room broadcasts: `room_update` (players/host/started), `room_gone`. `indexList()` ships per room `{id,name,mode,cap,count,host,hostName,started,createdAt,names[≤8]}`, sorted live-first then newest-first.
- Client MP section (~line 16526+): `mpConnect` (auto-reconnect backoff, no loop; sends `hello` + `mpRefreshMyRooms()` on open), `handleMpMessage` (incl. `room_err` → `duoStatus` + `#mpBrowserStatus`), `mpEnterRoom`/`mpUpdateRoom`/`mpExitRoom` (diff-based join/leave system chat), `mpJoinRoom`/`mpCreateRoom`/`mpLeaveRoom`/`mpCloseRoom`/`mpRequestIndex`/`mpRefreshMyRooms`, view switchers `mpShowBrowserView`/`mpShowRoomView`/`mpRefreshViews`/`mpRenderRoomActions`/`mpRenderServerList`, status/player-list renderers (👑 host, 🔵 other player, ✓READY), chat (`mpAddChat`). `mpRenderServerList` rows = mode badge + name (gold **YOURS** badge when `mpMyRooms` has it) + `Host:` line + `👥 names`/"Empty — become host" line + right-aligned `n / cap players` pill, 🗑 (own rooms only, `confirm()` first) and Join/`● Inside`/FULL button; rows `flex-wrap:wrap` so the pill+buttons drop to their own right-aligned line on phones.
- **Keep-alive**: a 12s `setInterval` sends `{t:'refresh', clientId}` while the MP panel is open or a multiplayer match is running, refreshing the browser list and self-healing (`join_room` re-send) if the router ever rebuilds and drops an in-memory player list.
- Exports: `window.mpConnect`, plus debug hooks `window._mp()` (room/index/mine snapshot), `window._mpSend`, `window._mpRefreshMyRooms`.
- Gameplay: `squadStartMatch` (outpost, `G.multiplayer=true`, duoDiffMult 1, no revive), `duoStartMatch` (duoDiffMult 1.25, blue tint), `duoStart` (opens MP panel + creates duo room), `duoRender` (uses `roomReadyBtn`), `duoSetStatus`/`duoReset`.
- UI (~line 956-1013): status bar (`mpDot`/`mpStatusText`/`mpPlayerCount`/`mpRefreshBtn`) + `mpBrowserView` (server list, host box) + `mpRoomView` (badge/name/copyInvite/host/`duoStatus`/players/chat/start/ready/leave). Old `duoPanel`/`startOutpostBtn`/`startDuoBtn`/`outpostCard` removed. Duo is a room mode inside the Server Browser (`roomModeSelect`); the main-menu `storyBtn` was removed.

## Boosts (shop consumables)
- `BOOST_DEFS` (index.html ~line 2031) maps a boost key to `{ name, icon, price, desc, apply(G), tag? }`; the Shop's *Boosts* tab renders one `shopCard` per entry (generic loop, so adding a key is all that's needed). `ownedBoosts` (localStorage `zzg_boosts`) counts stacks; buying appends a count. `startGame` resets `G.coinMult`/`G.reloadMult`/`G.mysteryLuck`/`G.reviveCharges`, consumes **one of each owned type** per match (`activeBoosts`) and calls each `apply(G)`.
- Optional `tag` renders the same pastel pill used by gun skins/calling cards, in the card between the price and the `Owned: n` line.
- Five originals: `hpboost` Health Crystal (+50 max HP), `speed` Wind Scroll (+20% move), `dmgboost` Spirit Charm (+15% damage), `ammboost` Coin Magnet (×1.5 coins), `fastreload` Swift Hands (−30% reload).
- **`luckybox` Lucky Draw (🎲, 🪙350, tag New)** — `apply` sets `G.mysteryLuck = 2`. `mysteryWeight(k)` (next to `mysteryWeaponPool()`) returns `MYSTERY_WEIGHTS[k] * luck` for rare weapons (`weight <= 10`), `/ luck` for common ones (`weight >= 15`), unchanged in between. Both roll sites in `rollMysteryBox` (the cycling display and the final reveal) use it, so the on-screen cycling also favours rares. Measured: rares (weight ≤ 10) 46.6% → 73.8%, legendaries (weight ≤ 3) 4.1% → 7.0%.
- **`secondwind` Second Wind (💚, 🪙400, tag New)** — `apply` sets `G.reviveCharges = 1`. The very first thing `gameOver()` does is check `G.state === 'playing' && G.hp <= 0 && G.reviveCharges > 0`; if so it consumes the charge, restores `G.hp = maxHp/2`, sets `G.player.iframe = 150`, floats + banners "💚 SECOND WIND!" and **returns without ending the match** (so it also fires before the duo "go down" branch). All 7 damage-death call sites just do `if (G.hp <= 0) { G.hp = 0; gameOver(); }` and nothing after, so returning early is safe. Without a charge the match ends exactly as before.

On `G.state !== 'playing'` it calls `clearSentry()`.
  - `fireSentryShot(ent, kind, tY)` — tracer `THREE.Line` (pushed to `G.tracers`), a muzzle particle + additive burst, 4 impact sparks at the hit point, then `damageBoss(SENTRY_DMG)` / `ent.hp -= SENTRY_DMG; if (hp <= 0) disableAnimatronic(ent)` / `killZombie(ent)` by `kind`, and a `beep(1150, …)`.

  - **No lights**: the turret creates zero dynamic lights by design (see Perf notes) — every glow is additive geometry, including the muzzle burst.

## Perf notes
- Too many `PointLight`s (>~20) can stall the first-frame shader compile and freeze the preview — outer torches are lightless for this reason. Ceiling uses an up-pointing DirectionalLight + emissive material instead of many point lights.
- **Runtime light-count changes are the big one**: three.js keys its compiled shader programs on the *number of lights in the scene*, so **adding or removing any light mid-game recompiles every material**. On weak/software-GL browsers each compile is ~0.5-1.8 s, so the first mid-game light change has been measured at ~10 s (and, while the sentry briefly used two PointLights, ~13-30 s) of frozen preview. Confirmed trigger: `createPowerupDrop`'s `PointLight` (removed when the drop expires or is taken) → stack `createPowerupDrop < grantZombieKillRewards < killZombie`. The same one-time-per-session stall will fire from the first camera muzzle light (`_cameraMuzzleLight`), the sniper/requiem impact lights (~12212/12213), the AAT/PaP/nuke flashes, fireball/meteor lights and explosion lights. `window._scene.traverse(o => o.isLight)` counts the current lights; `window._renderer.info.programs.length` shows the program churn. Preferred fix if this is ever tackled: a **fixed pool of pre-added lights** (intensity 0 when idle, always `visible`) that every transient effect borrows from, so the light count never changes — or pre-warm the extra light counts behind the loading screen.

## Viewmodel hands (first-person) — dual-wield grip fix
- `makeArm(mode, flip)` in `buildViewmodelHands` builds the single first-person hand used by every gun: a `fist` box (0.12×0.10×0.13) closed **behind** the handle, a `knuckles` block in front of it, a `thumb` (offset in x by `flip ? -1 : 1` — the only mirrored part, which is what makes it a left hand), a sleeve `cuff` and a `forearm` dropping away down the arm (`sleeveMat`). `mode === 'fist'` (dual-wield only: `akimbo`, `dualsmg`) no longer builds anything different — the same hand is used, one per handle, then moved onto that handle.
- **Twin Lotus (`akimbo`) had hands sunk inside / oversized around the grips**: the fist was previously built from hand-measured *arm-local* numbers and an earlier edit had multiplied those by 1.346 without the matching `hands.scale` change, leaving the hands ~35% too big and too far from the eye. The wrap-around "fraction of the handle box" fist that briefly replaced it read as floating slabs in-game (fingers barely bit the front strap, tips hovered 0.2 grip-widths off the inboard face).
- **Current approach**: the single pistol's own hand placement is measured once, relative to its pistol handle, and reused for each dual-wielded handle — `PISTOL_HAND_IN_GRIP` (`x/y/z` in handle widths, `rx/ry/rz` for the pistol hand's small tilt, `scale` = hand size per handle width). `fitFistGrip(arm, gripMesh, handScale, flip)` walks the tagged handle (`userData.isGrip` on `buildSinglePistolModel`'s and `buildStormTwinSmg`'s grip box — the handles are collected as `fistGrips` from `currentVmGun`, left first, right last) up to `viewmodel`, composes `handleMatrix * PISTOL_HAND_IN_GRIP` (mirrored via `M·L·M` for the left hand), decomposes it into the arm's `position`/`quaternion`/`scale` (divided by `hands.scale`), and rewrites `userData.basePos/baseRot` so the reload/bob offsets still work. The `hands.scale.setScalar()` values for `akimbo`/`dualsmg` are therefore irrelevant to these two arms (the size comes from the handle), and no per-weapon hand offsets are needed.
- Verified: in-game the `akimbo` hands sit on the grips exactly like the single pistol's hand (same geometry, same proportion to gun scale — hand ≈ 0.35 of the gun's bbox vs the pistol's 0.42), no gaps/clipping, and it scales correctly for `dualsmg` (its own, smaller handle) with no code changes.
- To retune, change `PISTOL_HAND_IN_GRIP` only (it is a pure handle-relative measurement: bigger `scale` = bigger hands, `z` moves them toward/away from the shooter along the backstrap axis). Re-measure with: for `pistol`, `rel = inv(grip.matrixWorld) · hand.matrixWorld`, then `rel.decompose()`.

## Requiem revolver viewmodel — placement fix
- The Gatekeeper revolver (`requiem`, key `2` in Gatekeeper mode; not buyable, not in the mystery pool, so the viewmodel is the only place it appears) used to be the **smallest and lowest gun in the game**: at `scale 1.2` its grip was anchored to the pistol's, so the small revolver hung down into the bottom-right corner (measured gun pixels 12094 vs the pistol's 16309 in the same 488×274 frame — that is what "the position is wrong" looked like).
- Now (branch ~line 9178): `gun.scale.setScalar(1.5)`, `gun.rotation.set(0, 0.07, 0)`, `gun.position.set(0.1275, -0.0118, -0.4158)`. The position is derived, not eyeballed: `pistolGripWorld = pistolPos + Ry(0.07) * gripLocal * 1.78 = (0.1327,-0.188,-0.3409)`, then `pos = pistolGripWorld - Ry(0.07) * (0,-0.1175,0.05) * 1.5`. After the change the revolver's grip lands in camera space at exactly the pistol's (0.1327,-0.1881,-0.341) and it fills the frame like the pistol (13532 vs 12257 gun pixels).
- `gripFit = !!armMode || key === 'requiem'` (in `buildViewmodelHands`, ~line 8694) routes the revolver's hand through the same `fitFistGrip` path as the dual-wield hands, so the fist is sized from the revolver's own handle width via `PISTOL_HAND_IN_GRIP`/`PISTOL_GRIP_WIDTH` (the revolver grip is beefier, so its hand is proportionally bigger — `hands.scale` 0.85 for this key is irrelevant to that arm). Nothing about `PISTOL_HAND_IN_GRIP` or the akimbo/dualsmg hands was changed.
- `MUZZLE_POS.requiem` (~line 9942) was `[0.14,-0.04,-0.62]`, i.e. ~0.37 units **behind** the true muzzle, so the flash appeared mid-barrel. Now `[0.10,-0.20,-0.82]`, weighted from the muzzle's recoil sweep (fire frame pitches the viewmodel −0.45 rad, so the muzzle drops; weighted muzzle ≈ (0.088,−0.238,−0.869)). Verified on a fired-frame capture: the flash sits at the muzzle.
- Known/accepted: the Requiem never takes the player's gun skin (`const skipSkin = key === 'requiem'`, ~line 9100) — it always renders as dark steel + gold. Untouched; change that line if skinning it is wanted.
