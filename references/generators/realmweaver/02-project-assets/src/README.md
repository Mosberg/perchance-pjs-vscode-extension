# Realm Weaver — Handoff Note

An AI-directed text-adventure RPG on Perchance ("you weave your own world, forge heroes, live endless stories"). The AI (`generateText`) acts as game master; `generateImage` renders location backgrounds, portraits and scenes; gallery worlds are shared via comment channels. The whole app is a large (~18.4k-line) single `<script>` in `index.html` plus a config/list `main.pjs`.

## Entry points
- `main.pjs` — perchance lists & config: `$meta`, `generateText`/`generateImage`/`kv`/`uploadPlugin`/`superFetch` imports, `commentsPlugin` options, `galleryOptions` & the two custom gallery buttons (EXIF embed, fullscreen, download, remove-background via HuggingFace transformers, AI-text-on-image canvas editor), plus `unsafe` moderation lists. Small random lists at top: `npcName`, `tavernName`, `questHook`.
- `index.html` — all HTML + CSS + app JS. CSS is a theming system with 8 color themes + 6 font pairs via `:root[data-theme=…]` / `:root[data-font=…]`. The app JS begins after the markup (`<div id="gameApp">`) — functions start ~line 3176 (`BASE_CLASSES`, `REGIONS`, `PRESET_WORLDS`, `state`, GM config, then render/game functions). Scroll to the `// INIT` section near the end for boot wiring.
- `src/music/*.mp3` — per-genre BGM tracks referenced by URL. They ship with the generator (uploaded so the URLs are permanent).

## Flow (creation → game)
1. 18+ **age gate** → 2. **world selection** (`#worldSelection`: create-custom / preset worlds / saved adventures / shared player worlds) → 3. **character creation** (`#charCreation`) or **custom world forge** (`#customWorldCreation`, `#cwGenProgress` step-by-step progress: lore→regions→factions→cast→classes) → 4. **game screen** (`#gameScreen`, `#storyPanel` with the story log; popup/dock panels: party, characters, factions, inventory, map/atlas, quests, chat; floating story-summary, notes, world-info; background/scene lightboxes; world map SVG).

## Recursive place tree (Sep 2026)

Regions no longer hold a flat list of sub-locations. Each region now owns a recursive tree of PLACES that can nest to **unlimited depth** — e.g. `region → metropolis → district → building → room`, or as little as `region → a single wilderness spot` (a wilderness region with only flat children, or none at all). Every tier is optional; the AI (and the player) decide how deep a given region goes.

### Data model
- Each region is also the ROOT node of its own place tree (there is no separate same-named "home" child any more).
- Every place node: `{ id, name, kind, desc, children: [], scene?, bgUrl?, ... }`. `kind` is a best-effort label (`metropolis`/`town`/`district`/`building`/`room`/`wilderness`/`landmark`/`place`) used only for glyphs and prompt hints; it does not constrain nesting.
- **Party position** = `state.world.currentPath`, an array of child IDs from the region root down (`[]` = standing at the region itself). The legacy leaf string `state.world.currentLocation` is kept in sync for the many existing call sites. The location is ALSO mirrored onto the **protagonist hero object** (`state.party[0].currentRegionId`/`currentLocation`/`currentPath`) by `syncProtagonistLocation()` (Sep 2026), called from every location writer — `setCurrentPath`, `normalizeCurrentPath`, `syncPathFromCurrentLocation` (including both of its early-return branches, so arriving at a region root or a missing region still mirrors), `buildProtBundle`, and `updateLocationLabel` (the per-turn re-assertion choke point). NOTE: new-adventure setup (`initGame`/`initGameWithAppearance`) and `startNewProtagonist` deliberately leave `state.world.currentLocation` falsy (`null`/`""`) — that falsy value is the sentinel `generateOpening` checks to AI-craft this hero's unique starting sub-location (`if (!state.world.currentLocation) generateStartingSubLocation()`), which then calls `setCurrentPath` and mirrors. Do not normalize the location during those setup functions or the starting place is skipped. `protagonistHero()` returns the `isPlayer` hero. So the tracked location always belongs to the PROTAGONIST, never an NPC or a stale container; the atlas extractor context and prompt name "the protagonist <name> and their party" explicitly. The protagonist-switcher chips' tooltips show each hero's full place breadcrumb, using the LIVE `state.world` location for the active hero (their bundle only catches up on switch/forge) and their own bundle location for the others.
- **`region.locations` is DERIVED, not authoritative** — `syncRegionFlat(region)` rebuilds it from the tree (`placeFlat`). Never write to it directly; mutate the tree and resync. This keeps ~200 legacy call sites working.
- Each node caches its own `scene` + `bgUrl`, so moving between places swaps the background per node.

### Helpers (function declarations near the old `regionPlacesToText`, ~line 9595 — all hoisted)
`newPlaceId`, `nodeChildren`, `guessPlaceKind`, `placeKindGlyph`, `makePlaceNode`, `placeFlat`, `syncRegionFlat`, `migrateRegionPlaces`/`ensureRegionHomeLoc`, `normalizeRegionHomeLocs`, `currentRegion`, `placeByPath`, `placeBreadcrumb`, `currentPlace`, `findPlacePath` (whole-tree name→id-path, shallowest wins), `currentPlaceName`, `placePathLabel`, `placeOutlineText`, `setCurrentPath`, `gotoPlaceByName`, `addPlaceChild` (dedupes within parent + resyncs the flat index), `materializeDeclaredPlaces` (creates a whole declared hierarchy parents-first), `normalizeCurrentPath`, `syncPathFromCurrentLocation`.

### Where the tree is honored
- **AI narration prompt** (`buildStoryPrompt`): GAME STATE Location = the full breadcrumb; the region place tree printed as an indented outline; CURRENT SCENE says places can nest arbitrarily and teaches the `parent` field. Other prompt sites (scene image, NPC free-will, companion image, idea/action helpers) show `placePathLabel(...)` too.
- **Atlas extractor** (`extractAtlasChanges` + `extractorContext`): the `locations` array takes an optional `parent` (exact name of the existing place the new one sits inside), and the prompt asks for a whole new hierarchy outermost-first. `kind` enum includes `metropolis`.
- **`applyStateChanges`**: resolves a destination by name anywhere in the tree (`findPlacePath`); materializes declared places first (`materializeDeclaredPlaces`); naming the region itself returns to the region root; a genuinely new distant name creates a new region; a small place inside a locked region adds nothing.
- **Header location dropdown** (`updateLocationLabel`/`buildPlaceOptions`): one `<optgroup>` per region, options indented per depth with kind glyphs; the value encodes the id-path (`r:<regionId>` or `p:<regionId>:id|id|…`) via `encodeLocationValue`/`decodeLocationValue`.
- **Locations panel** (`renderMap`): the current region's card shows a clickable breadcrumb (`placeBreadcrumbButtons`) and buttons for the current node's children — or, at a leaf, its siblings (`placeChildButtons`), wired to `travelToPlacePath(regionId, path)`.

### Region editor text format
The region editor's **Places** field edits the tree as indented text — two spaces (or one tab) per level, a line is `Name` or `Name — description`:
```
Crown Metropolis
  Market District
  The Gilded Keep
    Throne Room
The Rugged Wilds
```
`regionPlacesToText` writes it, `parsePlaceLines` reads it, and `mergePlaceNodes` merges edits back onto the existing tree by name so node ids, kinds, and untouched deep children survive (the current path therefore stays valid across edits).

All colors/fonts are CSS custom properties (gold `--accent` on dark `--bg` by default; light themes `ivory`/`frost` wash the shared background light). When styling anything new, use the CSS variables so the theme system keeps it consistent. Buttons use `--btn-from/--btn-to` gradients. Fonts via `--font-display`/`--font-body`. 8 themes: gold, crimson, emerald, ocean, violet, ash, ivory, frost.

- Persistence is per-user via `kv`. Shared-worlds gallery is comment-channel backed. Files in `src/` ship with the generator; `scratch/` is ephemeral.
- **Output language setting** (Sep 2026): GM Instructions ▸ Narration has a **Narration Language** dropdown (`#gmLanguageSelect` + a hidden `#gmLanguageCustom` text input), stored as `state.gm.language` / `state.gm.languageCustom` (default `"auto"`). `GM_LANGUAGE_PRESETS` (~35 languages + "Other…"), `populateGmLanguageSelect()`, `syncGmLanguageCustomVisibility()`, and the `fillGMSettingsFromState`/`readGMConfigIntoState`/Reset wiring keep it in sync. `activeLanguageName()` resolves it (`"auto"`/empty → `""`). `languageClause()` (prose) and `languageJsonClause()` (structured) are the tailored clauses used by the story, quick-action, extractor, starting sub-location, NPC free-will, auto-action, idea, enhance and companion-chat prompts; **`outputLanguageClause()`** is the universal clause that `gmText()` appends to EVERY AI text call — so narration, NPCs, summaries, equipment/item names, quests and world text all come out in the chosen language. `gmText` skips the append when the instruction already contains a `LANGUAGE…:` clause or when the call sets `_noLang:true`; the two image-prompt builders (`buildScenePrompt`, `ccAskImage`) opt out because image models should stay in English. - Shared-world payloads (since Aug 2026) are **gzip-compressed** before upload (`gzipText` in `shareCurrentWorld`) and decompressed on download (`fetchSharedPayload` — magic-header `0x1f 0x8b` detection, so old uncompressed shares still load). Region `bgUrl` base64 data-URLs are stripped from the shared snapshot (both the standalone `regions` copy and `fullState.world.regions`) because they're personal AI art that regenerates on load — they used to blow the upload size limit and made turn-1 worlds unshareable.
- `root.kv.sharedWorlds` cache has legacy format drift (entries stored as `[code, record]` arrays under numeric keys rather than code keys) — `renderCachedSharedWorlds` handles both, but there can be a small grid/cache count mismatch.
- **Surrender outcomes wired** (Sep 2026): surrendering used to always run the "robbed" branch (`applySurrenderConsequences` — forfeits the fight's stake + 25% gold), leaving `decideSurrenderOutcome`/`applyJailConsequences`/`applyEnslavementConsequences` unused. Now `syncCombatFromNarration` calls `applySurrenderOutcome()`, which dispatches on the fight's `stakesType` (from the combat extractor; or, when absent, a heuristic on the enemies' names/desc): `robbed` → stake item + 25% gold, `jailed` → weapons + all gold confiscated, `enslaved` → all gear + gold confiscated, `eaten` → the whole party is devoured (HP 0 → game over). `combatForcedOutcomeNote("surrender")` — used by the story `task`, the quick-action `actionPrompt`, and both inline COMBAT STATE prompt sites (which now just call the helper) — is outcome-aware so the GM's narration matches the mechanical cost, including the FATAL wording for `eaten`. The flash message is prefixed per outcome (imprisoned/enslaved/devoured).
- No `server-plugin` is imported — the game is fully single-player/local + AI. Adding it would be a big architectural step (see below).
- **Save files are slim** (Sep 2026): the ACTIVE protagonist's bundle used to duplicate the whole top-level state inside every save (each save was ~2× size). `slimSaveState` strips that payload from saved copies; `loadSave` rebuilds it on load (bundle lacking `story` = slim). Saves are capped at the 5 newest per world + the world's first save, enforced by `pruneWorldSaves()` after every save/import and at boot; `migrateSavesToSlimFormat()` repairs pre-slim saves once (localStorage flag `rw_saves_slim_v1`). Auto-save (`scheduleAutoSave`) skips when `stateSignature()` is unchanged, and all saves serialize through `enqueueSave` so prune sweeps can't race.
- **Story/container sync discipline** (Sep 2026): every background AI state extraction captures `storyRevision` when it starts and **discards its result if it changed mid-flight**. `storyRevision` is bumped not only on story delete/regenerate/rewind but on every story-container swap too — protagonist switch (`activateProtagonist`), forging a new hero (`startNewProtagonist`), fresh adventure (`initGame`/`registerInitialProtagonist`), main-menu return, and save load. That way a sync still running for hero A can never land inside hero B's state (or a wiped/reset one). The switch/forge paths additionally `await waitForStateSync()` before swapping so the leaving hero's in-flight updates are applied to THEIR container first, not lost. If you add a new path that replaces or clears `state` (or swaps `state.activeProtId`), it must also `storyRevision++` — otherwise stale extractions will corrupt the new container. Extractions are serialized, so a task can also sit QUEUED behind a slow sibling while the container swaps; `enqueueStateExtraction` therefore captures `storyRevision` at ENQUEUE time and drops the task (releasing the queue) if it changed before the task starts — otherwise a queued task would capture the already-bumped revision when it began and sail past the in-flight guards into the new container. `STATE_PANEL_IDS` (party/inventory/map/char/quests/factions) is the full set of panels extraction can update, so all six get the "Updating…" overlay while their sync is in flight. The story-summary AI sequences (background compaction, and the ⟳ summary refresh/regenerate) capture `storyRevision` the same way and drop their result if it changed, so a chunk/summary written for now-deleted entries can't be re-appended after a rollback.
- **Background-tab resilience** (Sep 2026): browsers throttle/freeze hidden tabs — long AI stream connections get cut, timers slow to ~1/min, and the stall watchdog stops firing on schedule. The game now (1) records `lastHiddenAt` on `visibilitychange` and re-runs `checkAiStallRecovery()` (the old watchdog body, extracted into a named function) the instant the tab is visible again; (2) **defers background state-extraction tasks while `document.hidden`** (`enqueueStateExtraction` holds the task via `waitUntilVisible`, capped at 2 min) so panels don't try to sync with AI calls that would die hidden; (3) auto-pauses the AUTO loop while hidden; and (4) gives a narration round whose AI connection died while hidden **one automatic re-run when the player returns** — in `runGM`'s catch (any error, `!roundCommitted`, `tabHiddenSince(state.busySince)`, revision unchanged) and after `autoContinueNarration` when the text is still incomplete. The round's busy lock is held through the wait (capped 150 s); on success the dead entry is removed and `runGM(task, opts)` re-runs; if the player never returns the round ends via `failRunGmRound` with an honest transcript note. Helpers: `lastHiddenAt`, `waitUntilVisible(maxMs)`, `tabHiddenSince(ts)`, `failRunGmRound(entryEl,textEl,btn,msg)`. New background/swap logic that fires AI calls should also gate on `document.hidden` where the work is invisible to the player anyway.
- **Single concurrent AI generation — extractors are SERIALIZED** (Sep 2026): the AI provider resolves only ONE `generateText` call at a time; firing several at once leaves all but the first hanging until their stall deadline. A real turn proved it: three parallel extractors returned the first in 8 s while the other two both died at the 120 s stall guard — which is exactly why the **World Atlas / Known Characters** overlays (the narrative track) sat on "Updating world atlas… / Updating known characters…" for ~2.5 min every turn ("always stuck"). `extractStateChanges` now runs ATLAS → MECHANICAL → COMBAT → CHARACTERS **strictly one after the other** (each returns in a few seconds; each track's overlay lifts the moment it lands). The **ATLAS pass runs first (Sep 2026)** so the world atlas establishes the party's place before the MECHANICAL/protagonist pass runs — the party/protagonist panel is therefore synced against the location the narration just established, and its "Updating protagonist…" overlay lifts AFTER "Updating world atlas…" rather than before it. (Don't move MECHANICAL back in front of ATLAS.) The old combined NARRATIVE extractor was **split into two focused calls** (Sep 2026): **ATLAS** (`extractAtlasChanges` — party location/travel, sub-locations, region description, scene → `mapPanel`) and **CHARACTERS** (`extractCharacterChanges` — new/changed NPCs, removals, party membership, party appearance → `charPanel`). Smaller, single-purpose prompts do each job better, and they run ATLAS first so the character tracker sees the party's freshly-updated location when it resolves NPC movement. The ATLAS pass **re-runs once** whenever it creates a brand-new place (a sub-location of the current region, or a whole new region) that the party didn't end up at: the first pass often registers a new place in `locations` without emitting the matching `location` move, so the second focused pass — with the new place now recorded, listed in the shared context (`; known places here:`), and called out via the `newPlaces` note — reliably moves the party into it and finishes describing it. `snapshotLocationState`/`locationGrewBy` detect the new places from the pre/post state diff. The two other parallel-AI sites were serialized too: the custom-world forge (`generateCustomWorld` — lore/regions then class) and `generateOpening` (civilian leader then starting sub-location). **Rule: never fire two `generateText`/`gmText` calls concurrently — chain them.** As a belt-and-braces guard, `enqueueStateExtraction` also lifts all six panel overlays after `STATE_EXTRACTION_OVERLAY_SOFT_MS` (20 s) regardless of whether the sync finished, so a slow provider can never leave panels dimmed for minutes (the sync keeps running and its results still render as each track lands).
- **Quest-objective sync** (Sep 2026): the mechanical extractor now sees each active quest's existing objectives with their ✓/☐ done state (`extractorContext`'s "Current quests" line), and `applyStateChanges` matches the AI's `objectivesDone` entries to objectives **by text, not by array index** — so a step finished out of order ticks the right box instead of blindly ticking the first one. Re-sending an `objectives` list without `objectivesDone` no longer wipes completed steps (done state is carried over by text match), `objectivesDone`-only updates apply against the existing list, and positional booleans/indexes are still accepted for models that return them. The GM prompt's "Active Quests" line also lists each objective's done/todo state so narration stays consistent with the quest panel.
- **Name-keyed container sync on rename** (Sep 2026): a character's relationship, private chat log (`companionChats`), and mood are keyed by their lowercased NAME. The AI rename path (`npcUpdates.name`, the RENAME RULE's preferred route) used to change `npc.name` without moving those keys, so the character silently lost their accumulated relationship (score/notes/summary/chunks) and private conversation history. `renameCharacterKeys(oldName,newName)` now migrates `relationships`, `moods`, `companionChats`, and `currentNpc` to the new key, called from the AI `npcUpdates` rename branch AND from the NPC editor's `readCommon` (which previously recreated the relationship from form fields, dropping summary/chunks). It never overwrites an existing target key. Note: the extractor's fallback rename route (create a new `npcs` entry + list the old name in `removeNpcs`) still can't carry history — the prompt prefers the uid rename for exactly this reason.
- **Known NPCs never "tag along" unless the story shows it** (Sep 2026): already-known NPCs used to drift after the party — in ROAMING `npcMovement` mode `moveTravelingNpcs` moved ANY named NPC mentioned in a travel narration, and the tracker's ambient `npcUpdates {nearby:true}` / `{location:…}` teleported a mentioned NPC to wherever the party now stood. Now an NPC relocates to follow the party ONLY when the narration EXPLICITLY shows them accompanying it (same-sentence accompaniment language with their name, and no "stays behind" language) — a mention, memory, discussion, farewell, or the party merely having traveled never moves anyone. Shared gate: `narrationShowsNpcAccompanying(narration, name)` (regexes `NPC_TRAVELS_WITH_RE`/`NPC_STAY_RE`), `npcDestIsPartySpot(dest)`, and `npcMayFollowToPartySpot(npc, narration)`; enforced at every apply site — `moveTravelingNpcs`, the `npcs`-fold path for an existing NPC, and both `npcUpdates` branches (locked + unlocked). Independent moves are still free: an NPC's own `location` anywhere that is NOT the party's region/spot always applies (roaming autonomy preserved), and brand-new NPCs still spawn at the party's spot. The three prompt sites that used to instruct NPCs to come along were tightened to match: `GM_NPC_MOVE_TEXT.rooted`/`.roaming`, the character extractor's NPC TRAVEL RULE, and the quick-action prompt's NPC TRAVEL note. `npcMovement: "roaming"` now means "NPCs pursue their own goals across the world", not "NPCs follow the party".
- **NPC free-will round no longer silently skipped** (Sep 2026): the round ran only on turns where `narrationIndicatesTravel(cleanText)` was false, but that detector matched ANY travel-ish phrasing regardless of who was moving — so ordinary GM prose about an NPC ("…giving you a curt nod as he prepares to depart toward the manor") was misread as the PARTY traveling, and the round was skipped on most turns, making NPC agendas look like they never fired. The detector now requires the **party/player as the mover**: only the PARTY subject list (`TRAVEL_PARTY_SUBJ`: you/thou/we/your·our·the party·group·hero…) followed by a travel phrase counts. The gap between subject and verb (`TRAVEL_GAP`) may span an intervening clause ("you leave X and journey to Y") but must stay within one sentence and must NOT cross a third-person subject (`he|she|they|who`), the conjunction `as`, or a determiner-led noun phrase (`the|a|an|his|her|their|its` + a word) — that is what stopped an NPC's movement ("…as he prepares to depart…", "You see the stranger leave the village") from reading as the party's. `TRAVEL_GUIDE_RE` now takes only party objects (you/us/the party/the group/the hero) and `TRAVEL_FINDWAKE_RE` only `yourself|myself` / `you|we|I|the party` as the waker, so "the steward leads them…" or "she finds herself…" no longer count. Travel phrasings the detector used to MISS were fixed too: the `set` strong phrase now covers the -s/-ing forms ("the party sets out"), the movement+direction rule allows a direction adverb before the preposition ("you march onward toward the keep"), and the wake/find rule allows a two-word gap before the place noun plus `cell` in the place list ("you wake in a cold stone cell"). Verified 29/29 real moves (incl. multi-clause) → travel, and 26/26 stay-put / NPC-movement sentences → NOT travel (no residual false positives). The deliberate trade-off remains: a missed move is harmless (the round just runs one beat late), whereas a false "move" silently skipped whole rounds. The decide prompt was also rebalanced (aim for 1–3 actions incl. an independent agenda move, instead of "usually 0 to 2"/most do nothing), the resolve prompt no longer primes failure ("Reasonable, well-suited actions by capable characters generally SUCCEED… do NOT default to failure") and now separates PLAYER AGENCY from NPC failure (an NPC's attempt may genuinely land even when it concerns the player), and `actionPowerNote` rewrites "the player's" → "each character's". Verified live: the round now fires on ordinary stay-put turns (2 NPC actions rendered `⟐ Name …` + resolved), and in `mature`/`nsfw` genre an explicit NPC action (hug/fondle) renders and the real AI resolves it without refusal or fade-to-black. NB the game routes all AI calls through the classic-script global `gmText()`, but internal call sites bind to a scope-local reference — reassigning `window.gmText` does NOT intercept them (use a temporary guarded hook in `runNpcFreeWillRound` if you must inject test actions).
- **Automatic location changes now STICK** (Sep 2026): the atlas tracker's explicit `location` was applied only when `narrationIndicatesTravel()` — the strict, party-subject-anchored regex built for the NPC-round skip — also fired. That detector is deliberately conservative (subject-anchoring is what stops an NPC's movement reading as the party's) and MISSES a large share of real travel prose: on a 39-line battery it missed 13, e.g. "you head for the capital", "you descend into the catacombs", "you go upstairs", "you march east through the fields", "after an hour's walk, the gates of X rise before you". Every location-apply branch was gated on that flag, so roughly a third of real moves were silently dropped — the party stayed in their old place (map, scene, and context wrong). New gate `partyMovedTo(narration, locName, changes)` (next to `narrationIndicatesTravel`) treats the AI's `location` as the semantic decision and only requires the narration to CORROBORATE it: (a) the strict detector fires, OR (b) the destination is a place the AI established this turn (`changes.locations`) or one named for the focused follow-up pass (`changes._newPlaces`, tagged onto the atlas result by `extractAtlasChanges`), OR (c) a single sentence both NAMES the destination and shows movement into it (`TRAVEL_CUE_RE` — broad party-agnostic verb list), with `TRAVEL_CONTEMPLATE_RE` disqualifying consideration/memory/discussion sentences ("you wonder about the temple"), OR (d) the destination is an already-KNOWN place (`isKnownPlaceName`: a region or an existing node of the current region's tree) and any non-contemplative sentence shows movement — this last branch catches AI-normalized names that differ from the narration's wording ("the capital" for "Eldermere") and can never spawn a phantom region. A genuine new region still requires the destination name to appear in a movement sentence or be newly declared, so pure mentions can't teleport the party. `narrationIndicatesTravel` is UNCHANGED and still used for the NPC-round skip (its conservative misses there are harmless). Verified live: 11/12 realistic move lines apply (incl. nested known + new-declared + whole-new-region, with the protagonist mirror updated), 8/8 mention/contemplation lines blocked.
- **Relationship standing shown to the GM** (Sep 2026): the main narration prompt's GAME STATE now appends `npcRelPromptNote(n.name)` to each NPC present in the scene — the relationship label/score plus up to 140 chars of condensed shared history — so GM narration stays consistent with the relationship container the UI shows. Neutral characters with no recorded history are omitted (no noise).
- **Async AI results pinned to the container they were started for** (Sep 2026): two more places where an in-flight AI write could land against the wrong *current* container state. (1) Shop inventory: `generateShopInventory` now captures `getShopInventoryKey()` at start and files the result under THAT region key — previously it wrote `state.shop.inventories[state.shop.location]` and set `state.shop.inventory` using whatever region the player was in when the AI returned, so traveling/reopening the shop mid-generation filed one region's stock under another. Only the newest generation (`shopGenToken`) owns the loading flag/repaint, and `shopGenInFlight` (a Set of region keys) stops `openShop` firing a duplicate request for a region already generating. (2) Relationship summarizer: `maybeSummarizeNpcRel` captures `storyRevision` and, after the AI returns, drops its condensation unless the revision is unchanged AND `state.chat.relationships[key] === rel` — otherwise a summary of now-rolled-back notes was appended as a chunk pinned to the post-rollback message length (which rollback trimming could never remove).
- The world-selection "Create Your Own World" CTA was redesigned (Aug 2026) into a premium card `.create-own-card`.
- **Two mandatory behaviour blocks added to the GM narration prompt** (Sep 2026): a "check the ai instructions and improve it" pass over `buildStoryPrompt`'s literal text. Added **NPC KNOWLEDGE & SECRETS** (every NPC knows only what they could plausibly know — never the player's private thoughts, off-screen events, or unrevealed secrets; knowledge must not leak between characters or from narrator to NPC) placed after `gmClusters.npcCompetence`; and **DEFEAT & FALLING** (HP is the sole authority on life/death — never narrate the protagonist's death while HP > 0, and when HP reaches 0 narrate a genuine fall with no rescue pulled from nowhere; matches `checkGameOver`/`isPartyDead` firing on `hero.hp <= 0`) placed after `gmClusters.actionPower`. Both are hardcoded (not player-toggleable), like ANTI-REPETITION. A TIME & ENVIRONMENT CONTINUITY block was tried and REMOVED at the user's request (the model handled time continuity badly) — do not re-add it. Also removed a duplicated "Allies act autonomously based on their class and skills." clause from the inline COMBAT block (the PARTY SYSTEM block already states it, with "personality").
